## Native capacity evidence

Installed projectzomboid.jar methods inspected offline: ItemContainer.getEffectiveCapacity(IsoGameCharacter):int, getCapacityWeight():float, getContentsWeight():float, hasRoomFor(IsoGameCharacter,InventoryItem):boolean, floatingPointCorrection(float):float; InventoryItem.getUnequippedWeight():float. getContentsWeight iterates actual inventory instances and adds getUnequippedWeight once per item. getCapacityWeight delegates to this for ordinary storage; character/dead-body inventories have special paths. Effective capacity includes native organized/disorganized adjustments. hasRoomFor includes special-container/native restrictions and remains a mandatory independent hard check.

Native ISInventoryTransferAction uses getUnequippedWeight and floatingPointCorrection for floor accounting. Floor special cases are not imported into storage allocation. Allocation storage accounting uses the native unequipped-weight getter, including its native nested-content contribution, without recursively counting bag children again or multiplying UI stacks. Existing Trips.getActualWeight reservations are not proof of correct nested allocation weight and will not be silently reused as the allocation unit.

## Decisions before implementation

1. One sparse profile: default percentage, explicit category quotas and exact FullType item quotas. A category edit stores one explicit aggregate ceiling and removes descendant overrides; inherited percentages are presentation/default values, not duplicate aggregate restrictions. An item must satisfy every applicable explicit ancestor ceiling plus its own explicit ceiling, against the same capacity basis; percentages are never multiplied.
2. The current resolver exposes one flat native category. Do not invent Food/Perishable/Raw Meat or revive the retired B47 taxonomy. The engine supports verified parent paths, but shipped native categories have no invented ancestors. Mod headings remain presentation groups and cannot become category quotas. Duplicate display names require an exact-FullType choice/subrow for independent allocation edits; legacy selections remain shared by name.
3. Missing allocation preserves the legacy rules exactly and imposes no additional ceiling. Existing unchecked rows are not rewritten as destructive false rules. New allocation is an additional constraint on legacy eligible storage, never an access/selection grant. Unknown item/category overrides remain persisted and visible as orphaned configuration.
4. Use schema-3 configuration envelopes with read support for schema 2; no automatic schema-only rewrite on read. Explicit save preserves a recoverable original snapshot before replacing an old envelope. Presets and furniture parents retain complete profiles and existing priorities/inheritance. No player save is used for migration testing.
5. Room quotas use authorized, inspectable, deduplicated physical compartments in complete verified geometry. For each explicit category/item ceiling, denominator is the sum of effective capacities of physical destinations that pass native item restrictions and legacy hard selection rules for the routed item. Initial proposal: occupancy within the same eligible set. Corrected before enforcement: matching aggregate occupancy counts all supported physical room stock internally, including opaque compartments, while those compartments add no capacity. This conservative denominator/occupancy split prevents cross-actor access subsets from double-spending shared quotas; no private contents or counts are returned. Logical parents/ground/placed/unauthorized/unloaded storage add no capacity. Incomplete scope is unknown, never a truncated permission to deposit. Every overlapping active room profile must allow a deposit independently.
6. Fill thresholds use current total native used weight plus relevant pending incoming weight over the same item-compatible physical-capacity set. This is distinct from category matching occupancy and quota ceilings. Full eligible storage still contributes to the denominator; unrelated/ineligible furniture does not. Threshold comparison is >=. Defaults confirmed by user: Primary 60%, Secondary 80%.
7. Preserve existing match specificity and explicit container priority before room preference. Within equally ranked candidates of the same room type, aggregate eligible Primary and Secondary groups; Secondary at/above its return threshold prefers Primary, else Primary at/above overflow prefers Secondary, else prefer Primary. Missing preferred groups fall back to valid alternatives. Multiple groups use explicit priorities then stable room IDs/physical identity; no random winner. Unassigned storage remains available as deterministic fallback. Freeze preference for a bounded planning batch, recheck hard constraints at grants.
8. Stage rollout starts in server-controlled shadow mode; advisory jobs do not mutate inventories or block the first legacy transfer on a full scan. Authoritative activation remains gated on migration, capacity, regressions, authority, explained shadow differences and native-transfer compatibility. Native/dedicated gates cannot be claimed from host fixtures.

## Risks and preserved state

Display names are legacy selection identity, not safe identity for new numeric item overrides. Broad/subcategory examples are not present in the active taxonomy. Client-local Better Containers categories require exact item choices and cannot establish authoritative server taxonomy. Current capacity reservations are per-run, not global allocation reservations; two-client quota admission needs a separate server-owned bounded ledger and completion reconciliation. Private contents cannot be scanned just because a user can configure metadata. Old clients must be rejected for new configuration capability; old save decoding does not imply downgrade safety. Recoverable snapshots support deliberate rollback, not automatic old-version loading of schema 3.

Development occurs in isolated feature worktrees. Original Auto Clean edits and existing 0.8/0.1 packages remain unchanged. No deployment, server change or Workshop staging/publication is authorized. G6 native acceptance NOT TESTED; G7 dedicated NOT TESTED/BLOCKED; stable G8 BLOCKED.
