## Track A — Category audit: BLOCKED, not fixed

[VERIFIED native source/bytecode] Script Item.displayCategory is shared definition metadata. Item.InstanceItem copies it through InventoryItem.setDisplayCategory(String). Runtime InventoryItem.getDisplayCategory() reads its own string field, and its setter writes that field. The JAR-wide field/call-reference audit finds runtime field access only in getter/setter and category getter use in InventoryItem.isMemento; save/load do not read/write that field or call its getter. Thus a runtime override is not an established replicated/persisted category mechanism; reconstruction from definitions must be distinguished from item serialization. Evidence: dist/handoffs/dev29-category-relevant-references.json; full native reference inventory retained separately.

[VERIFIED Lua] ISInventoryPane.refreshContainer at 2170 sets row.cat to getDisplayCategory() or getCategory(); 2178 sorts with the active comparator. Category comparators at 242-253 compare row.cat with name tie-breaking. renderdetails at 2546-2549 looks up IGUI_ItemCat_<native category>. These are raw keys, not translated sort labels. The canonical Quartermaster resolver at Categorizer.lua:442 resolves ScriptItem identity and caches by script and ClassifyToolsByUse; display overrides on inventory instances would not themselves change that classification cache. Modded scripts use the same canonical fallback and ranked evidence. No new resolver cache or per-frame scan was added.

[VERIFIED gameplay coupling] ISInventoryPaneContextMenu.lua:221 identifies bullet/ammo behavior by the native display category. InventoryItem.isMemento() also depends on the display-category getter. Script Item.getDisplayCategory is consumed by native loot-classification methods, so changing shared definitions can affect gameplay and diverge across server/client process definitions. Globally replacing these categories with B47 taxonomy IDs would not meet the handoff's no-gameplay-change constraint. This is a concrete boundary, not a claim that setters do not exist.

Decision: STOP metadata implementation under the no-gameplay-change requirement and authority invariant. Native category metadata is not safely interchangeable with a pure presentation label under the audited contracts. No category migration, definition rewrite, runtime item mutation, or new network state was introduced. InventoryCategories.lua and Categorizer.lua SHA-256 match dev.28. Existing draw-only adapter remains unresolved and native sorting remains vanilla. Passing transparency tests do not certify Track A.

Remaining design work: establish an original UI-owned display/sort model at verified inventory refresh/render boundaries that keeps native gameplay metadata intact, including the user's actual replacement-renderer chain. Alternatively a separately justified metadata design must explicitly preserve all native category consumers and authoritative lifecycle. Neither approach is assumed complete here. Native Category display AND sorting, modded/old/new items, refresh/reconnect, conflicts and dedicated MP acceptance all remain NOT TESTED/BLOCKED. This follows the attached handoff's Stage C instruction to report the blocker and leave Category behavior unchanged if safe integration cannot be established.

Better Sorting 2.1.5 remains capability-only research; no implementation, category data or assets imported. SOURCE CODE COPIED: NO. IMPLEMENTATION DERIVED FROM REFERENCE: NO.
